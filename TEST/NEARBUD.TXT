# Near data budgets of INV.EXE and of THIN, its network-only build
# (NEAR_EXES of MAKEFILE), checked by TEST/OMFNEAR.PY.
#
# Format: one "MODULE BYTES" pair per line; "#" starts a comment.  MODULE
# is an object file's name without .OBJ, BYTES the most static near data
# (DGROUP without the stack: initialised data, constants and string
# literals, zero-initialised data and near communals) that one object may
# hold under any of the three compilers (Open Watcom, Watcom C 6.5,
# Turbo C 2.01).  OMFNEAR.PY fails when a module is over its budget,
# when a module has no budget line, when the modules measured plus the
# LIB line exceed MAX_NEAR of TEST/mapchk.sh, or when all budgets
# together exceed MAX_NEAR.
#
# Every module is budgeted at its largest size under the three compilers
# plus a tenth of that size, rounded up, or plus 32 bytes where that is
# more; a module that grows past its budget is measured again and its
# line raised in the same change, as long as the total stays within
# MAX_NEAR.  Turbo C 2.01 gives most of the largest figures: it stores
# every repeated string literal again.  Buffers kept in far blocks, on
# the near heap or on the stack are not counted here.
#
# Why MAX_NEAR leaves room: DGROUP is one 64 KB segment holding the static
# near data (at most MAX_NEAR), the stack (_stklen of SRC/COMPAT/CDOS.C,
# the size every build links with) and the near heap, which holds the
# engine's handles and buffers with every table open and the client's
# list view descriptors and form values.  MAX_NEAR is set so that the
# heap keeps room to grow beside the other two.  Under Turbo C and Open
# Watcom INV and THIN hold their near heaps to the sizes their near-heap
# modules give: CMEM_NEARHEAP of COMPAT.H under Open Watcom, under Turbo
# C the smaller CMEM_INVHEAP of CMEMHI.C and CMEM_REMHEAP of CMEMHR.C, so
# that the part of DGROUP their static data, stack and heap leave goes to
# the far heap; TEST/mapchk.sh checks that MAX_NEAR, the stack and the
# heap fit.  The stack is checked separately, by the golden-screen runs
# of TEST/T_SCR.SH, which fill it with a pattern at start-up; only runs
# with /KEYS: do that, so the stack of INV /CMD is not measured.

# The C library's own near data (start-up code, stdio, heap state, the
# compiler's helper segments): the map's DGROUP total less the modules
# below, largest under Turbo C 2.01, with the same margin.  No object file
# holds it; it is only added to the total.
